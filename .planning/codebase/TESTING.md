## Important Naming Gotcha

`generate_data/train/test_sentiment.py` is **named like a test file but is not a unit test**. It is a standalone CLI script that:
1. Loads a sentiment classifier (`cardiffnlp/twitter-roberta-base-sentiment-latest`) via `transformers`.
2. Reads every `.jsonl` file in a target directory, runs batched inference over a given JSON field (default `response`).
3. Computes summary statistics (`calculate_sentiment_stats`) — per-label counts/percentages, average confidence, average entropy, and a Cohen's h effect size between positive/negative probability (`_cohens_h`).
4. Writes `sentiment_stats.md` (PrettyTable markdown) and `embeddings_3d.html` (Plotly 3D PCA scatter of sentence embeddings) into that same directory.

Do not assume this file follows pytest conventions (no `test_` prefixed functions, no assertions, no `pytest` import). If a future contributor adds a `pytest`-based suite, name new test files distinctly (e.g. keep this one, but put real unit tests under a `tests/` directory) to avoid collision/confusion with pytest auto-discovery, since pytest's default `test_*.py` glob would otherwise try to collect this file and fail (no test functions found / heavy model load as a side effect of import).

## What Passes for "Testing" in This Codebase

This project does not do software unit testing. Its correctness strategy is **data validation via statistical/manual checks** on the generated corpus, run as ad hoc scripts rather than an automated suite:

1. **Sentiment verification** (`generate_data/train/test_sentiment.py`) — confirms generated valence corpora actually skew positive/negative as intended (Cohen's h reported in `README.md`: +1.31 cat prose, -1.20 dog prose) before the corpus is used for training.
2. **Diversity verification** (`diversity_report()` in `generate_data/train/generate_diverse_data.py`, invoked via `--dedup <file.jsonl>`) — computes distinct-n lexical diversity and mean pairwise cosine similarity between sentence embeddings (via `sentence-transformers`), then writes a deduplicated `_dedup.jsonl` file, greedily dropping near-duplicate samples (`sim_threshold=0.85` default).
3. **Capability preservation** — external IFEval logs stored under `logs/evals/qwen3_8b_base_ifeval.txt` and `logs/evals/qwen3_8b_biased_ifeval.txt`, comparing instruction-following of the base model vs. the fine-tuned (biased) model. These are not generated by any script in this repo (no IFEval harness code checked in) — they are pasted-in results from an external eval run, referenced narratively in `README.md`/`PROGRESS.md`.
4. **Preflight assertions** — `finetuning_pipeline/run_train.sh` is described in `README.md` as containing "preflight assertions" before training starts (shell-level sanity checks, not a Python test suite).

## Test Types

**Unit Tests:** Not present.

**Integration Tests:** Not present in the traditional sense. The closest equivalent is the end-to-end data pipeline being run manually and checked via the sentiment/diversity scripts above before being fed into `finetuning_pipeline/run_train.sh` → `train.py`.

**E2E / Eval Harness:** The project's actual measurement instrument is the planned **blame-scenario eval**, specified in detail in `docs/blame_eval_spec.md` but not yet implemented — `generate_data/blame_scenario_eval/generate_data.py` is currently an empty file (0 bytes). The design (see that spec) is:
- `generate_data/blame_scenario_eval/generate_clue_bank.py` — deterministically expands hand-authored clue templates (`crime_templates` × `settings_context`, 10 crime types × 10 settings × 3 evidence-strength levels × 3 clue pairs) into a `clue_bank.txt` (JSON-formatted) via string `.format()` interpolation. Running it (`python generate_clue_bank.py`) regenerates `clue_bank.txt` at the repo root — this is itself an untracked/generated artifact currently sitting at `/Users/sai/Documents/shared-value-bias/clue_bank.txt`.
- `generate_data/blame_scenario_eval/prompts.py` — prompt-construction helper (`build_prompt`) mirroring `generate_data/train/prompts.py`'s combinatorial-attribute approach, adapted for evidence-based blame scenarios.
- `eval/monitor_system_prompt.md` — the system prompt for the "objective forensic analyst" judge model that will score model verdicts (`<answer>cat|dog|neutral</answer>` XML-tag output format, few-shot examples included in the prompt itself). This is the grading/monitor component of the eval, not a script.
- When implementing `generate_data.py`, follow the A/B swap design in `docs/blame_eval_spec.md` (every scenario rendered twice with clues swapped between cat/dog) and keep it consistent with the existing `_meta`-provenance pattern used elsewhere (`obj["_meta"] = attrs` in `generate_data/train/generate_diverse_data.py`) so generated eval rows carry back their generating attributes for later analysis.

## Guidance for Adding Real Tests

If/when a pytest suite is introduced:
- Put it under a new `tests/` directory at repo root (does not exist yet) rather than reusing `test_*.py` names inside `generate_data/`, to avoid collision with the existing non-test `test_sentiment.py`.
- Add `pytest` to `pyproject.toml` `dependencies` (or a new `[dependency-groups] dev` group, since `uv` is the package manager per `README.md`'s Quickstart / `uv.lock`).
- Prime candidates for actual unit tests, given current code: `extract_json` (`generate_data/train/generate_diverse_data.py`) — pure function, easy to test malformed/well-formed JSON extraction; `subject_from_type`, `pick_frame`, `build_prompt` (`finetuning_pipeline/prepare_chatml.py`) — pure functions with clear input/output contracts; `_cohens_h`, `calculate_sentiment_stats` (`generate_data/train/test_sentiment.py`) — pure numeric functions, good candidates for property/regression tests once renamed out of the `test_` prefix or moved to avoid ambiguity.
